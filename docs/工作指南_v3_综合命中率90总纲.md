# 第一部分 全景：项目结构与 token 经济学拆解

## 1.1 流水线结构

千笔一文的逐章生成流水线，每章约 9-10 次 LLM 调用，按序为：

```
卷纲/细纲 → 章正文(prose, thinking 高档) → 字数闸门
  → 扩写(enrich, 字数不足时 1-2 轮) → 本地 L0 确定性预检
  → AI 味扫描/去味(deslop, 整章重写) → 6 维审校(review, 3 票并行 + CISC 置信聚合)
  → 审校修复(review_fix) → 超长压缩(trim, 超标时) → 章摘要 → 全局摘要(每 2 章)
  → 追踪台账(JSON 补丁) → 设定清算(canon_audit, in-session)
```

每章约 13 章 130 笔调用 ÷ 13 章 = 10 笔/章。模型 DeepSeek 官方 deepseek-flash
（thinking 默认开启、默认 effort=high——这个"默认"是后面大量分析的根源）。

## 1.2 单次请求的解剖（逐段 token 构成）

以第 N 章审校调用为例，一次请求的字节序列是：

```
[system] 冻结稳定头（head_rebuild 模式，v8 起）
  ├─ 全书前缀 project_header（题材预设/核心设定/正则 must 契约）
  ├─ PROSE 指令库（S4：写作指令模板化冻结版）
  ├─ 卷首冻结快照（设定底册/世界书/卷纲——头 v2 新增）
  └─ 审校静态尾段（review_in_system：裁决优先级+六维 checklist+输出契约）
[轮 1] 本章开幕轮：八节章头（细纲/全局摘要/角色状态/时间线/伏笔/上章结尾）+ 写作动态值
[轮 2] 本章正文（草稿或补尾后的完整稿）
[轮 3..k] 本章已发生的相位轮次（去味/审校票/追踪补丁的请求与回复）
[轮 k+1] 本次审校请求：SCOPE 行 + 动态材料（findings/引证）+ 静态指令（若未前置）
```

关键结构事实：
- **system 段（冻结头）卷内逐字节不变**——每章、每次调用都完整重发，但因逐字节
  相同而全部命中（命中价 1/31）；
- **开幕轮（轮 1）每章一次性新贴**（miss 一次），此后在本章内被后续调用复读（命中），
  在下一章被丢弃（head_rebuild 语义：跨章历史不入栈）；
- **每个相位的轮次 = 静态指令 + 动态材料**——静态指令若不进冻结头，就会以
  「每章一份」的速度在历史里累积（v6 时代追踪相位整本重述、撞 8192 截顶的根源）。

# 第二部分 事实基础：为什么敢这样设计

## 2.1 服务商语义六条（官方文档 L + 黑盒实证 E1）

1. **完整前缀单元命中**：请求必须完整匹配某个已持久化单元，部分匹配不命中；
   单元在请求边界（输入尾/输出尾）、公共前缀检测、超长输入固定间隔三时机持久化。
2. **best-effort**：持久化不保证及时——实测「首达深度的请求按 miss 计价，同字节
   5-15 秒后重放命中 99.9%」（E0 探针，263k 栈 8 级扫描）。
3. **写延迟 ≈ 一个发次**：v10 实测审校末票（hit 99%）后 2-5 秒的清算首笔只记到
   头部（-65~-81pp，13/13 章零例外）——这是 audit 鲸鱼的机制，加 45 秒窗后修复到
   53.1%（+26.4pp）。
4. **TTL 无硬保证**：闲置数小时至数天清除——停更后首章需预热，属预期成本。
5. **超长输入固定间隔切分**：单元粒度随栈长变粗——栈越长，章界脆弱面越大。
6. **命中价差 31 倍、off-peak 半价**：DS 官方 deepseek-flash 命中价 off-peak 低至
   $0.0035/M——大头头在离峰时段近乎免费复读。

## 2.2 我方 E1 实测十条（全部有产物证据）

1. 卷会话使 20 章命中率 80.4% → 93.8%（T1）；无界栈使 53 章成本 5.9 倍（T3）；
2. 静态冻结省 ~11-12k token/章（S4）+ 审校尾段 ~3.3k/章（V1-③）；
3. 台账 JSON 补丁（v2.1）：追踪输出不再随章数截顶，13 章 4.3k/章均值；
4. head_rebuild 模式逐章 prose 入参平坦于 ~18-29k tok（v8/v10 双跑确认）；
5. **压缩是质量装置不是成本装置**（T2：不省钱但盲评 +1.03）；
6. **正文思考长度百倍方差**（323 ~ 32,770 tok，同配置）——输出侧最大不确定项；
7. effort low 输出 -36%（V9 三章实测）；
8. audit 写延迟窗 +26.4pp（v10 实测）；
9. 章界记账税 ~¥0.03-0.05/章，不可优化，口径纪律绕过（E0 定案）；
10. 真实台账污染事故（cost_bench 模块级 app.usage 导入）已修复并写入反模式。

## 调整一 冻结头扩容：全相位静态指令库并入（头 25k → 40k tok）

### 做什么

把追相位之外仍在「每章轮次里逐章重发」的三份静态指令库，全部并入冻结头的卷首
快照文件：

1. **设定清算指令尾段**（canon_audit 的 AUDIT_PROMPT 静态部分，约 4.5k 字符）——
   从 AUDIT_PROMPT 模板中切出「你是网文世界观的合规审校」之后、第一个含章号
   动态插值之前没有的静态区段（对齐 review_static_tail 的提取器模式，新增
   audit_static_tail 函数）。注意：AUDIT_PROMPT 的首句含「第 {num} 章」，静态段
   的切点必须在所有 {num} 插值之后。
2. **追踪补丁协议说明段**（TRACKING_PATCH_PROMPT 的 JSON schema 与硬规则段，
   约 3.2k 字符）——schema 与规则是纯静态，动态的只有「本章正文/现状表/出场
   清单」等材料槽。提取器同上，切点在「## 本章正文」之前把指令头段（你是供
   程序读取的状态补丁器…输出格式说明）取静态化，材料槽留在轮次里。
3. **去味指令基座**（DESLOP_REWRITE_PROMPT 的通用规则段，约 1.5k 字符）——
   口头禅黑名单与去 AI 味红线全部静态；逐章变的只有正文本身。

三段并入卷首冻结快照文件（`追踪/冻结头快照_卷N.md` 的结构化升级版：改存
`冻结头快照_卷N.json`，内分 sections 字典，每段独立可渲染），由
head_rebuild_system_text 按序拼接渲染。

### 为什么

问题根源：这三份指令库目前随每章轮次进入会话历史。设指令体为 I token、每章
该相位调用 c 次，则第 k 章结束时历史中累积的该相位指令字节约为 k × I——**第
k+1 章的每次调用都要按命中价复读这 k 份冗余**。v10 实测：清算材料+指令每章
入栈约 12.6k miss + 数十 k 命中价复读；追踪 4.3k 输出 + 5.3k miss。

原理（缓存语义）：指令体移入 system 段的冻结头后，字节位置从「每章追加的新
深度」（首贴必 miss、此后每章复读）变为「卷首固定深度」（首贴一次 miss、此后
全卷每次调用命中）。代价是每次调用的输入多了这份指令的命中价读量——但命中价
是未命中的 1/31，且**取代的是历史里按章累积的 N 份副本**，净效果严格为正。

外部依据：Anthropic static-first 原则（官方文档明言 static 部分跨会话缓存复用）、
Aider 四层排列（system → read-only → repo map → editable，最常变的放最尾）、
Claude Code 91.9% 命中的架构基础就是大而稳的 system 段。

### 实现原理

- 提取器：`audit_static_tail()` / `tracking_patch_static_head()` /
  `deslop_static_rules()`，模式对齐已有 `review_static_tail()`（标记切点 +
  单元测试钉住切点不漂移）；
- 头构建：`head_rebuild_system_text()` 增加三段并入（顺序：卷系统 → 设定底册
  快照 → 清算尾段 → 追踪头段 → 去味规则 → 审校尾段）；
- 轮次瘦身：对应相位的 session_turn_text 调用改为「已前置版本」——把模板中的
  静态段以同一标记切除，只 format 动态材料；
- 一致性守卫：快照文件在卷首生成后逐字节复用；卷中途代码升级导致头变化时，
  既有 load 机制自动拒绝旧栈并告警（既有行为，零新代码）。

### 预期效果（数字推导）

并入量：清算 4.5k + 追踪 3.2k + 去味 1.5k ≈ 9.2k 字符 ≈ 6.9k tok（按 0.75 换算）。
头从 25.3k → 约 32k tok。

- **每章 miss 削减**：这些指令此前每章随轮次首贴 miss 一次 ≈ 6.9k miss/章
  （v10 实测 audit miss 15.1k 中约一半是指令与材料的混合首贴）；
- **每章 hit 增加**：头每调用多读 6.9k × 9.5 调用 = 65.6k 命中价读 ≈ ¥0.0014/章
  （可忽略）；历史里少累积 6.9k/章 × 12 章 = 83k 的复读量（省 ¥0.013/章起，
  且随卷长放大）；
- **净效果**：miss/章 -6.9k、综合命中率分母中 miss 占比下降、章界脆弱面缩小。

### 预注册门槛

- 清算/追踪/去味相位的**裁决质量不降**：指令只是换了位置，模型看到的内容等价
  （同一会话内 system 与轮次内容模型都可见）；雷章召回 B01/B02/C01/D01 不降；
- 头尺寸实测 32k ± 2k tok；快照文件卷内逐字节稳定（二次构建 diff 为空）；
- prefix_lint 全绿；全量回归全绿。

### 回滚

三段并入由 `writing.instruction_in_head` 旗标控制（缺省 false）。关闭时：
头构建跳过三段、相位轮次回退全量模板——与 v10 请求体逐字节一致。

## 调整二 相位边界写延迟窗：审校→清算修复的推广

### 做什么

v10 已在「审校→清算」边界加入 45 秒写延迟窗（复用 session_pace_seconds，修复
后 audit 命中 26.7% → 53.1%）。本轮做两件事：

1. **窗口细化**：把全局 session_pace_seconds 拆为按边界的细粒度配置
   `pace_boundaries`（JSON：{"prose→review": 45, "review→audit": 45,
   "audit→下章": 0, ...}），缺省保持现状；离峰时段可全开。
2. **推广评估**：用 v10 的逐相位 miss 数据（§1.3 表）判定哪些边界值得加窗——
   判据：边界后首笔的 miss 增量 > 3k tok 且该增量在后续同章调用中被命中回收
   （证明是写延迟而非真 miss）。预计 prose→review 与 deslop→review 两个边界
   达标；其余边界增量小不值得等。

### 为什么

原理（E0 实测）：服务商把请求字节写成缓存单元有 5-15 秒延迟。流水线相位衔接
通常在 2-10 秒内——下一相位的首笔请求会把自己刚写入、尚未可读的上游字节按
miss 计价。v10 的逐章数据：audit 在 review 末票（hit 99%）后 2-5 秒只记到头部，
13/13 章零例外——确定性机制，不是抖动。

为什么要窗而不是重试：写延迟是服务商语义（best-effort），重试同一请求只会
重复付费（首发的 miss 已经付了）；等待窗口让「下一个调用」读到的单元变成
可读状态，把本会 miss 的字节转化为命中——离峰时段 45 秒的机会成本接近零。

### 实现原理

`_pace_after_long_call` 已实现单调时钟等待 + ctx.stopped 打断。本轮改动：
1. 函数增加 `boundary` 参数（字符串，标识哪个边界）；
2. `pace_boundaries` 配置查表取该边界的秒数，查不到用全局缺省 0；
3. 在清算/追踪/去味的调用点各插入对应边界的 pacing 调用。

### 预期效果

v10 实测 audit 边界加窗：hit 26.7% → 53.1%（+26.4pp），相当于每章 miss
-8.5k ≈ **-¥0.065/章**。推广到 2-3 个达标边界，预期再 -¥0.03~0.05/章。
**延迟代价**：每章 +90~135 秒墙钟（离峰窗口资源闲置，无现金成本）。

### 预注册门槛

- 墙钟增量记录在案，不得静默超过 3 分钟/章；
- 对照判定：同边界关窗重跑 1 章，miss 差异可复现。

### 回滚

`pace_boundaries` 删除对应条目即回退；函数缺省 0 不影响任何既有路径。

## 调整三 全相位 effort 纪律：卷内统一 + 机械相位降档

### 做什么

1. **卷内统一**：prose/review/audit/deslop 等全部调用在同卷内使用同一
   reasoning_effort 档位，卷界才允许切换（防止 Think Max 的 system 前端注入
   打死冻结头）——在 Orchestrator 卷启动时锁定档位并写进 state，卷中拒绝变更。
2. **机械相位降档**：canon_audit 的 effort 从 high（连接缺省）降为 low——
   依据：V4 报告 High/Max 差距只在 HLE/Apex 难题，清算属对照检查任务；且
   v10 实测 audit 推理占输出 46%（26.4k/12 章 = 2.2k/章）。deslop/enrich/摘要
   维持现状（已 disabled 或已 low）。
3. **prose 档位裁决实验**（独立 A/B，盲评门）：prose effort high → low 一次
   对照——依据：overthinking 文献与 V4 报告自承创作 over-thinking；但创作
   质量敏感，必须过盲评 D2/D4 ≥ -0.5 才转正。

### 为什么

官方 thinking_mode 文档的档位映射是本轮调研的最有价值发现：medium/high/xhigh
全部映射 high——**我们配置里所有写 medium 或 high 的调用实际都在付同一个
最高档的钱**。机械相位（对照检查/格式转换/摘要）在该档位下的额外思考链对
裁决质量无可测增益（V4 Table 7：High/Max 差距集中在 HLE/Apex 难题），纯粹是
分母里的死重。

风险与缓解：effort 档位可能向 system 前端注入指令（Think Max 行为，官方 V4
报告 §5.1.1）——同章混用档位会导致冻结头前缀失配。缓解：卷内统一 + 卷界切换；
且「注入只发生在 max 档」的实测若成立，low/high 混用的风险更低——保守起见
仍统一。

### 实现原理

`_mk_cfg` 的三条测试连接已显式携带 thinking/effort。改动点：
1. Orchestrator 卷启动：读 `writing.volume_effort`（缺省 "high"），写入 state
   与全部连接的 effort 字段；
2. canon_audit 的 S2 分支构造 client 时 effort 取 "low"（固定，随旗标
   `audit_effort_low` 缺省 false）；
3. 变更章界生效：卷中途改档 → 既有 load 拒绝机制兜底。

### 预期效果

audit effort low：推理 2.2k/章 → ~0.8k/章（文献 CoT 压缩 40-60%），
**输出桶 -1.4k/章 ≈ 综合命中率 +1.5pt**；延迟 -40%（audit lat 17.1s 主要在
思考）。prose low 实验（若盲评过）：推理 3.7k/章 → ~1.2k/章，输出桶 -1.8k/章
≈ +2pt，且延迟 -40 秒/章。

### 预注册门槛

- audit low：雷章召回 B01/B02/C01/D01 不降（E9' 关思考换来 59% 引证不实的
  前车之鉴——这次是 effort low 不是关思考，且引证验真在环）；
- prose low（独立 A/B）：盲评 D2/D4 ≥ -0.5；
- effort 档位写入 state，卷内不可变（测试钉住）。

### 回滚

两档都是连接/调用级参数，删除即回退；state 里的档位记录支持审计。

## 调整四 投票紧凑 schema：审校票输出最小化

### 做什么

6 维审校票的输出从「六维长文分析 + 引证原文」改为**紧凑 JSON**：
`{"dim": "...", "score": 1-10, "quote_ref": "段N句M", "one_line": "≤40字"}`，
配合 `max_tokens: 900` 上限。引证验真机制不变（quote_ref 解析回原文片段后仍走
逐字验真），CISC 置信行保留。

### 为什么

依据（Lane B/C 双源）：MT-bench 实证长文分析不增加裁决可靠性（冗长偏置存在
但强 judge 一致率 >80% 已到天花板）；JSONSchemaBench 确认约束解码可靠保
schema；我们自己的数据：审校票 3 票 × ~590 tok = 1.76k/章输出 + 三票的请求
都带着前票引证的复读。

关键设计约束：**schema 过刚会把模型推离自然分布反而变长变差**（pr1nt.dev
实测）——因此不用硬约束解码（DeepSeek API 无 guided_json），用「提示词给
schema + max_tokens 硬上限 + 解析失败回退旧长文格式」的三层软硬结合。

### 实现原理

FINAL_REVIEW_PROMPT 尾部的输出契约改为紧凑 schema 说明（新模板
FINAL_REVIEW_COMPACT），解析器 parse_final_review_v2 增加 compact 分支——
字段名映射到既有 v2 结构（dimensions/score/quote），下游验真/聚合零改动。
旗标 `writing.review_compact`（缺省 false）。

### 预期效果

票输出 590 → ~300 tok（-49%）：三票 1.76k → 0.9k/章。**综合命中率 +1.3pt**
（输出分母缩小）。延迟 -30%（生成 token 减半）。聚合与验真逻辑不变。

### 预注册门槛

- 盲评：紧凑票与长文票对同章节的裁决一致率 ≥90%（分歧章双评仲裁）；
- 引证验真违规率不升（现状 0%）；
- max_tokens 截顶率 <5%（超限章回退长文格式重投）。

### 回滚

旗标关闭即回旧模板；解析器双分支长期共存。

## 调整五 L1 收尾：deslop/review_fix 的定点修复化

### 做什么

去味（deslop）与审校修复（review_fix）两个整章重写相位，改为**定点修复**：
只对命中的段落/句子输出替换对（沿用 span 模式的标注协议），本地合并。
与 E11/T4b 失败版的关键差异：**失败的根因是 span 模式让模型输出 JSON 编辑
列表（输出反而 5 倍）+ 无回退计数**；本次改为：

1. 命中段落 ≤2 处 → 模型只输出「段落号 + 替换后的段落全文」（纯文本、无 JSON），
   本地按段落号替换；
2. 命中 >2 处或替换后总长变化 >25% → 自动升级整章重写（既有路径）；
3. `writing.deslop_pinned`（缺省 false）；span_stats 落盘计数已就位（U1-c）。

review_fix 维持整章重写（修复常涉及跨段连贯，定点替换风险高），但其输出
已有 review_compact（调整四）的请求侧瘦身配合。

### 为什么

T4b/E11 两次实测 span 模式失败（输出 5 倍、+70% 成本），根因分析：模型输出
JSON 编辑列表本身耗费大量 token + 推理思考膨胀。段落号+纯文本替换把「编辑
列表」的输出压缩到只有替换文本本身；≤2 处的硬上限防止模型陷入多段重写。
理论上去味命中通常集中在 2-3 个重灾段（口头禅/排比滥用），替换文本量约为
命中段的 1.2 倍——输出 ≈ 整章重写的 15-25%。

### 实现原理

段落切分复用 span_edit.annotate 的段落标记（⟦Pnn⟧）；合并用 span_edit 的
段落替换原语（已存在，span 模式验证过解析健壮性）；合并失败（段落号越界/
替换后为空）自动升级整章。span_stats 继续记 pinned/fallback 计数。

### 预期效果

deslop 输出 0.9k → ~0.3k/章（-67%），deslop 输入不变；命中间接收益：去味
改写的段落入历史更短。综合命中率 +0.5~1pt。**门槛**：去味后 AI 味复扫通过率
不低于整章模式（既有复扫闸门自动把关）。

### 预注册门槛与回滚

- 去味复扫通过率 ≥ 整章模式 -5pp；
- span_stats.fallback 率 <20%（超限自动回退整章并告警）；
- 旗标缺省关，关闭时逐字节一致。

## 调整一 冻结头扩容：全相位静态指令库并入（头 25k → 40k tok）

### 做什么

把仍在「每章轮次里逐章重发」的三份静态指令库并入冻结头卷首快照：

1. 设定清算指令尾段（AUDIT_PROMPT 静态部分，约 4.5k 字符）——新增
   audit_static_tail 提取器（模式对齐 review_static_tail），切点必须在所有
   章号插值之后；
2. 追踪补丁协议说明段（TRACKING_PATCH_PROMPT 的 JSON schema 与硬规则段，
   约 3.2k 字符）——schema 与规则纯静态，材料槽（正文/现状表/出场清单）留轮次；
3. 去味指令基座（DESLOP_REWRITE_PROMPT 通用规则段，约 1.5k 字符）——口头禅
   黑名单与去 AI 味红线全静态。

三段并入卷首冻结快照（结构升级为 JSON，sections 字典分段子段独立渲染），
由 head_rebuild_system_text 按序拼接。

### 为什么

根源：这三份指令库目前随每章轮次进入历史。设指令体 I token，第 k 章结束时
历史中累积 k 份副本——第 k+1 章的每次调用都按命中价复读这 k 份冗余，且每章
首贴各 miss 一次。v10 实测：清算每章入栈 miss 12.6k（相位内最大）、追踪 5.3k。

原理（缓存单元语义）：指令体移入 system 冻结头后，字节位置从「每章追加的新
深度」（首贴必 miss、此后逐章复读）变为「卷首固定深度」（首贴一次、全卷每次
调用命中）。代价是每次调用多读一份命中价——命中价是 miss 的 1/31，且取代的
是历史里逐章累积的 N 份副本，净效果严格为正。这是 Anthropic static-first、
Aider 四层排列、Claude Code 大 system 段的共同原理。

### 实现原理

提取器三个（模式同 review_static_tail：标记切点 + 单测钉切点）；头构建函数
扩参；相位轮次构造改为「已前置版本」（同模板切去静态段）；卷中途升级由既有
load 拒绝机制兜底（旧栈自动拒绝并告警，零新代码）。

### 预期效果（数字推导）

并入量 9.2k 字符 ≈ 6.9k tok。每章 miss -6.9k（首贴消失）；每章 hit 读 +6.9k
× 9.5 调用（命中价 ≈¥0.0014，可忽略）；历史少累积 6.9k × 12 章 = 83k
（省 ¥0.013+/章，随卷长放大）。综合命中率 +2~3pt。

### 预注册门槛

清算/追踪/去味裁决质量不降（雷章召回 B01/B02/C01/D01 不降）；头尺寸 32k±2k
tok；快照卷内逐字节稳定；prefix_lint + 全量回归绿。

### 回滚

writing.instruction_in_head 旗标（缺省 false），关闭即全量模板回退。

## 调整二 相位边界写延迟窗：审校→清算修复的推广

### 做什么

v10 已在审校→清算边界加 45 秒窗（audit 命中 26.7% → 53.1%）。本轮：
1. 全局 session_pace_seconds 拆为按边界细粒度配置 pace_boundaries（JSON：
   边界名 → 秒数），缺省保持现状；
2. 推广评估：用 v10 逐相位 miss 数据判定哪些边界值得加窗——判据：边界后首笔
   miss 增量 > 3k tok 且该增量在后续同章调用中被命中回收（证明是写延迟而非
   真 miss）。预计 prose→review 与 deslop→review 两个边界达标。

### 为什么

原理（E0 实测）：服务商把请求字节写成缓存单元有 5-15 秒延迟。流水线相位衔接
通常 2-10 秒——下一相位首笔请求会把刚写入、尚未可读的上游字节按 miss 计价。
v10 逐章数据：清算在审校末票（hit 99%）后 2-5 秒只记到头部，13/13 章零例外。
为什么用窗不用重试：重试同一请求只重复付费；等待让下一个调用读到已写单元，
把 miss 转化为命中。离峰时段 45 秒机会成本≈0。

### 实现原理

_pace_after_long_call 增加 boundary 参数；pace_boundaries 查表取秒数；在
清算/追踪/去味调用点插入对应边界的 pacing。

### 预期效果

v10 实测审校边界：miss -8.5k/章 ≈ -¥0.065/章。推广 2-3 个达标边界预期再
-¥0.03~0.05/章。延迟代价：每章 +90~135 秒墙钟（离峰无现金成本）。

### 预注册门槛

≤3 分钟/章；关窗对照 1 章可复现差异。

### 回滚

pace_boundaries 删条目即回退；缺省 0 不影响既有路径。

（超限章回退长文重投）。

### 回滚

## 调整五 L1 收尾：deslop 定点修复化

### 做什么

去味相位改定点修复：命中段落 ≤2 处时，模型只输出「段落号 + 替换后段落全文」
（纯文本无 JSON），本地按段落号替换；>2 处或替换后总长变化 >25% 自动升级
整章重写（既有路径）。旗标 writing.deslop_pinned（缺省 false）。

### 为什么

T4b/E11 两次 span 失败根因：模型输出 JSON 编辑列表本身耗大量 token + 推理
膨胀。段落号+纯文本替换把输出压缩到只有替换文本；≤2 处硬上限防多段重写。
去味命中通常集中 2-3 个重灾段（口头禅/排比滥用），替换文本量约为命中段 1.2 倍
——输出 ≈ 整章重写的 15-25%。

### 实现原理

段落切分复用 span_edit.annotate 段落标记；合并用 span_edit 段落替换原语
（已验证解析健壮）；合并失败自动升级整章。span_stats 记 pinned/fallback。

### 预期效果

deslop 输出 0.9k → ~0.3k/章（-67%）；去味后 AI 味复扫通过率由既有闸门把关。

### 预注册门槛与回滚

复扫通过率 ≥ 整章模式 -5pp；fallback 率 <20%（超限自动回退并告警）；旗标
缺省关。

# 第五部分 两个更大架构动作与 95% 口径（v12 预研）

## 5.1 动作甲：冻结头扩到 60-120k（真材实料，非注水）

可并入冻结头的稳定内容远不止指令库——按「卷内逐字节不变」筛全书：

| 成分 | 规模（估） | 说明 |
|---|---|---|
| 全书前缀 + PROSE/审校/清算/追踪/去味指令库 | ~40k tok | 调整一 |
| 设定底册 + 世界书快照 + 卷纲 | ~19k tok | 头 v2 已含 |
| 本卷全部细纲快照（卷首冻结） | 13 章 × 2.5k 字 ≈ 24k tok | 细纲写定后不变 |
| 文风基座样本（3-5 章精选段） | ~8k tok | 卷首冻结 |
| 已完成章节的正文快照（卷首冻结，滞后一卷） | 惊人的量，按卷界冻结 | **这正是「有界上下文」的本体：上一卷全文以命中价常驻** |

后两项让头合法地长到 60-120k tok——**这不是注水，是把「跨章历史」从逐章追加
的累积栈改为卷界冻结的只读语料库**：同样的字节，同样的命中价，但位置从「无限
增长的尾」变为「固定大小的头」，每章新增材料与头的比例锁定，综合命中率因此
有界且可推算：

H=100k、章内 miss+out ≈ 30k 时：综合 = 900/(900+30) = **96.8%**。

质量边界（必须诚实）：100k 头重新进入 32-128K 衰减敏感区——但与 v7_long13 的
无界栈有本质区别：头是**有组织的冻结语料**（设定/大纲/前文按结构分层），不是
膨胀的冗余历史；且 T3 实测质量拐点在「跨卷累积 + 上下文膨胀」，冻结头的字节
稳定性恰好消除「膨胀」因子。**必须盲评裁决，预注册 D2/D4 ≥ -0.5。**

## 5.2 动作乙：输出极限治理（第二桶）

- prose effort low（盲评门）；
- 审校票紧凑 schema + max_tokens 900；
- canon_audit effort low + 输出上限 4k（清算 JSON 不需要长文）；
- 章内调用预算闸（每章输出总量超 30k tok 告警，超 45k 强制收束）。

理论：out 24.3k → 12-15k/章。

## 5.3 组合后的终局数学（v12 全量）

| 配置 | H/章 | M/章 | O/章 | 综合 | ¥/章 |
|---|---|---|---|---|---|
| V10 现状 | 273k | 78k | 24.3k | 72.7% | ¥0.253 |
| v11（七项调整） | 292k | 63k | 21.4k | 77.6% | ¥0.22 |
| **v12（+60-100k 冻结语料头 + 输出治理）** | **900k+** | **25k** | **13k** | **~96%** | **¥0.10-0.13** |

综合 96% 的另一面是成本：hit 读 900k×$0.0035（off-peak 对折）≈ ¥0.023/章 +
miss 25k×$0.11 ≈ ¥0.019 + 输出 13k×$0.33 ≈ ¥0.029 → **¥0.071/章（离峰）**。
即：**每章总成本有望进入 ¥0.07-0.13 区间，同时综合命中率 96%**——两个目标
在「大冻结头」架构下不是 trade-off 而是同向。

# 第九部分 逐相位深度解剖与专项优化

> 每章 9-10 次调用不是同质的——每个相位有自己的字节形状、成本结构与优化空间。
> 本部分对每个相位做完整解剖：请求构成、命中行为、成本占比、专项优化与判据。

## 9.1 prose（正文生成）——成本与质量的双重核心

**请求构成**：冻结头 25k tok + 开幕轮（八节章头 + 动态值，~12k tok）+ 写作指令
（已前置则无）。每章 1 笔，另有 0.6 笔补尾、0.5 笔扩写跟随。

**实测画像**：in/笔 25.7k、hit 58.7%、out/笔 5.5k（其中推理 ~3.1k——思考长度
百倍方差的重灾区，逐章 323~32,770 tok）。输出/章 3.7k tok。

**专项优化**：
1. 思考治理（最大单项）：prose 思考高档导致推理波动百倍——effort low A/B
   （盲评门）预期推理减半，输出桶 -1.8k/章 ≈ 综合 +2pt；文献依据：R2-Write
   （推理模型开放写作收益有限）、2602.16162（推理多样性负相关）；
2. **字数达标率**：v8_long13 的 13 章里 10 章首稿不达标触发扩写/压缩——大纲
   节点配额（每节点标字数）+ 首稿长度自检写进提示词（±10% 自检已有，加节点级
   配额分配）；每省一次扩写 = -1.2k 输出 -3.3k miss；
3. 上一章结尾与文风样本：head_rebuild 模式下这两节是跨章连续性的唯一载体，
   不可瘦身——但可从「上一章全文结尾 800 字」改为「上一章结尾 400 字 + 本章
   细纲衔接指令」，材料 -2k/章。

**判据**：prose in/笔 稳定 ≤22k；首稿达标率 ≥70%（现 30%）；盲评 D2/D4 不降。

## 9.2 canon_audit（设定清算）——miss 鲸鱼

**请求构成**：冻结头 25k + 本章全部轮次（开幕+正文+审校票+追踪补丁，~15-25k

miss——剩余部分是清算自身的新增材料首贴 + 更深的写延迟尾部。

**专项优化**：
1. 写延迟窗已落 ✓（+26.4pp）；
2. **S2 请求瘦身**：清算轮的台账块/底册条目名与冻结头快照重复度高——头 v2

6. **V2 首册拒绝**：空 base 拒合并 → 新角色进不了台账。检测：首章后角色
   sidecar 非空断言。已修（V6 冒烟发现）。
7. **effort 档位混用打死冻结头**（Lane A 警告）：Think Max 向 system 前端

9. **span 模式输出膨胀**：JSON 编辑列表 + 推理使输出 5 倍（T4b/E11 双证）。

10. **prompt 控思考遵循率 <25%**（ReasonIF）：思考治理必须走 API 参数。

# 第十六部分 常见问题（FAQ）

**Q1：为什么综合口径把输出算进分母？输出不是"生成的内容"吗？**
A：这是用户裁定的口径，工程上完全合理——输出 token 与输入 token 一样按
token 计费，且在 DeepSeek 的思考模式下推理 token 是输出的数倍。综合口径
把「生成系统的一切付费 token」置于同一把尺下，衡量的是「每支付一个 token，
有多少比例花在了可复用的前缀命中上」——它是**缓存架构效率**的度量，而非
「模型记忆能力」的度量。

**Q2：95% 与 90% 的差别到底有多大？**
A：综合 90% 意味着每 10 个付费 token 有 9 个是命中价复读或有效生成；95%
意味着 19 个。从 90% 到 95% 需要把（miss+output）再砍半——在头 60-100k、
章内新料 ~25k 的架构下，数学上就是「头再翻倍」或「输出再减半」。两者都
有硬边界（稳定内容上限 / 正文是不可压缩的产品本体），因此 **96% 左右是
本架构在本书上的理论终点**，95% 是可达的运营目标。

**Q3：为什么不直接换更便宜的模型？**
A：三桶中输出占 45-59%，换便宜模型降的是输出单价，但创作质量是产品生命线
（T2：草稿短 29%、盲评差 1.03 分的教训）。正确的省钱顺序永远是：先砍结构
冗余（不碰模型能力），再动采样参数（effort/思考），最后才考虑换模型——且
换模型=换缓存域=全部基线作废。

**Q4：冻结头里的世界书快照会陈旧吗？**
A：会——快照冻结在卷首，卷内反哺的新条目不在快照里。补偿机制：每章开幕轮
的「世界书（卷内增量）」段携带卷首之后的新条目（逐章追加、逐字节稳定）。
这条补偿链在 v11 的八节瘦身里必须保留。

**Q5：为什么审计命中率只有 53% 也算「修复」？**
A：修复前是 26.7%，写延迟窗翻倍到 53.1%。剩余 47% 中：清算自身新料首贴
（合理成本）+ 更深层的写延迟尾巴（下一档 90s 窗的实验对象）。文献与实测
都表明 100% 不可达（best-effort 语义），53% 已经让清算从「最大 miss 鲸鱼」
降为「中等贡献者」。

**Q6：如果 DeepSeek 改了缓存语义怎么办？**
A：本文的六条语义全部有黑盒探针可复验（provider_probe/replay/depth 三仪器），
任何语义漂移会在一次跑次内被发现（hit% 断崖 + 逐章曲线形状突变）。语义
模型是可证伪的——这是它区别于玄学的原因。
