## 0. 一页总览

**三类资源的真实约束**：

| 资源 | 约束 | 对策 |
|---|---|---|
| 真机 API（off-peak 时段） | 工作日 0-9 / 12-14 / 18-24 点 + 全周末半价；单章全流程 LLM 时间 10-15 分钟 | **全部长跑挂机到夜间/周末**；工作日午间 12-14 窗口只跑 5-16 分钟的固定草稿探针 |
| 子代理并发 | 计划按 **5 并发**设计；⚠️ 本会话调研时实测一次性派 5 个触发平台限流（仅 2 个成功），降到双发/逐发通过 | 车道**互相独立**设计，可无损降级为 2+2+1 波次（见 §2.3） |
| 人的注意力 | 是最稀缺资源 | **gate 制**：每天只做一次 30 分钟闸门评审，其余时间不盯 |

**核心时间经济学**：单变体 3 章全流程 LLM 墙钟 ≈ 30-45 分钟，人真正需要做判断的时刻只有"跑完之后看数据"的几分钟——所以一切设计围绕一条流水线：

```
白天(零API):  实现本轮代码 ──→ 预写下一轮代码 ──→ 分析昨晚数据 ──→ 30min gate
                                    ↓ 发车检查单
夜间(off-peak): 挂机队列 [变体A → 变体B → 变体C …]（每个跑完自动备份+续跑下一个）
                                    ↓ 晨报
次日白天: 分析 ──→ gate 裁决 ──→ 采纳/否决 ──→ 下一轮
```

**七天节奏总览**（模板，实际按 gate 结果滑动）：

## 1. 墙钟测算（排程的依据）

实测锚点（来自台账与实验报告 v1）：

| 负载 | LLM 墙钟 | 备注 |
|---|---|---|
| 固定草稿 3 章（清算系，12 调用） | 5-16 分钟（291-959s） | audit 系对照实验的实测量 |
| 全流程 3 章 | 23-32 分钟 LLM + 重试间隙 ≈ **30-45 分钟挂钟** | base 1383s / prose_med 1932s |
| 六章全流程（0.18.4 验收口径） | **~2h45m**（18:42-21:25，57 笔） | 0.19 级联+审校 disabled 后预计缩短 |
| 审校单票 | disabled 5.4s / high 82-215s | |
| 细纲单笔（high 档） | 431s | |
| 空流 | 全流程约每章 1 次，客户端关思考降级重发 | 每变体排程 +10% 余量 |

**窗口容量**：工作日 18-24 点（6h）≈ 8-10 个全流程变体；0-9 点（9h）≈ 12-15 个；周末全天 ≈ 20+。本战役全部实验（R0-R4 约 20 个变体跑）**三个夜间窗口即可装下**，瓶颈不在 API 而在白天的代码与雷集准备——这正是车道模型要解决的。

## 2. 车道模型（5 并发子代理）

### 2.1 车道定义

| 车道 | 职责 | 典型任务包 | 文件所有权（防冲突） | 产出节奏 |
|---|---|---|---|---|
| **L1 实现-当前轮** | 本轮实验需要的代码/prompt | span 解析器+合并器（E1.1）、长度预算 prompt（E1.2） | `app/pipelines/stages*.py`、`app/prompts*` | 每日 1-2 个包，半天盒 |
| **L2 实现-预备** | 提前实现下一轮，保证夜间队列不断粮 | provider 适配层（E4.1）、CISC 票 schema（E3.2）、清算早停 prompt（E3.3） | `app/llm/*`、新增模块 | 每日 1 个包 |
| **L3 分析-上一轮** | 消化昨晚/历史数据，产出裁决材料 | 相位级对比表、盲评结果汇总、台账行草稿 | 只读 `tests_output/bench/` + 写 `docs/` 分析节 | 每晨 1 份分析 |
| **L4 质量-雷集与盲评** | 埋雷法 v2 的雷集建设、核验、盲评组织 | 12-16 颗雷 + 双人核验记录 + 票序随机化（E3.1） | `tests/planted_defects/*`、盲评材料 | D1-D2 集中建设 |
| **L5 台账-工程杂务** | CI lint、观测口径、队列器、文档台账 | 前缀 lint（E0.2）、`bench_queue.py`（§5）、usage 口径（E0.3）、台账登记 | `scripts/*`、`tests/*`、`docs/成本台账.md` | 随包 |

**车道纪律**：① **文件所有权制**——每车道只改自己名下文件集，交叉需求走 gate 排队，禁止两车道同改一个文件；② 每包交付前子代理自跑相关单测（DoD 内置），不留人工往返；③ 一切交付物落到约定路径（见 §6 模板）。

### 2.2 依赖图（谁阻塞谁）

```
E0.2 lint ─┐
E0.3 口径 ─┼─→ E0.1 基线跑 ─→ G1 裁决 ─→ E1.1/E1.2 排程（算术重算）
bench_queue.py ┘
E1.1 span 实现（L1）─→ E1.1 夜间对照 ─→ G2
E1.2 prompt 变体（L1）─→ E1.2 夜间对照 ─→ 盲评（L4）─→ G3
雷集 v2（L4）─────────→ E3.1/E3.2/E3.3 全部质量断言
E4.1 适配层（L2）─────→ E4.1 外迁探针 ─→ G4
```

关键路径 = **雷集 v2**（E3.3/E3.2 的质量断言全依赖它）与 **span 解析器**——这两件 D1 白天必须开工。

### 2.3 限流降级策略（实测教训）

本会话实测：一次派 5 个子代理 → `user concurrency limit exceeded`（2 成功 3 失败）；降到双发/单发稳定。因此：

- **正常态**：5 车道各自有独立任务包，互不等待；
- **降级态**：按优先级波次发车——波1 = L1+L4（关键路径），波2 = L2+L5，波3 = L3（分析放最后是因为它依赖跑完的数据，天然靠后）；
- **设计规则**：任何工作包**不得**以"另一个车道的同时产出"为输入——依赖一律通过已落盘的文件（上一轮的产出），这样波次化零成本。

## 3. 每日 Gate（人的 30 分钟）

**议程模板**（固定五项，超时项顺延次日）：

1. 晨报过目（L3 产出：昨晚队列 × 变体的相位级对比表 + 异常清单）— 10min
2. 对照测试方案的**采纳门槛**逐条裁决：采纳 / 否决 / 加样本复跑 — 10min
3. 采纳项合并进默认配置（或用户可选档），kill criteria 触发项记录在案 — 5min
4. 今晚队列确认（变体清单 × 预算 × 窗口容量核算）— 5min
5. 台账新增行过目（L5 草稿）

**裁决记录去处**：调研报告 §3.2 的 O 表加"状态"列（待测/采纳/否决/部分采纳），测试方案对应实验卡片尾部追加一行结论——保证文档与事实同步。

## 5. 夜间发车 runbook

### 5.1 发车前检查单（队列器自动前置 + 人工 2 分钟确认）

- [ ] `git status` 干净，基线 commit 已打 tag（`bench/<日期>-<轮次>`）
- [ ] off-peak 窗口确认（工作日发车不早于 18:00；避开 9-12/14-18）
- [ ] **usage.jsonl 已备份切片**到 `tests_output/bench/<queue_id>/usage_backup.jsonl`（0.18.4 误截断 544 行的教训）
- [ ] 今晚变体清单写入队列文件，每个变体的预设 JSON 逐个 `python -c json.load` 通过
- [ ] 无人值守期间**不会有手动测试混入**（0.18.4 台账污染事故的教训；E2.2 后可按 user_id 天然隔离）
- [ ] 磁盘余量够（每变体产物 ~10-50MB）
- [ ] 变体预算合计核对（台账口径预演一遍）

### 5.2 队列器行为规范（`bench_queue.py` 的 DoD）

1. 逐变体串行执行 `cost_bench.py --variant <v> ...`；**变体间强制落盘间隔**（metrics/chapters/usage 切片归档到 `<variant>/` 后才启动下一个）；
2. 单变体失败：捕获、记录 `run.log`、**跳过继续下一个**（一夜不因一个变体报废）；同一变体内 LLM 空流走既有"关思考降级重发"路径；
3. 全停条件只保留两个：连续 3 个变体失败（疑似平台/网络级故障）、或成本超队列预算 1.5 倍；
4. 收尾产出**晨报** `night_report.md`：每变体一行（调用数/输入/hit%/输出/推理/成本/异常），相位级对比表自动生成（接 `cost_bench --compare`）；
5. 每变体完成即 `git add tests_output/bench/<variant> && git commit`（产物即证据，防丢失——5 章 e2e 被 rmtree 的教训）。

### 5.3 时间优化硬规则

1. **固定草稿探针走午间窗口**：12-14 点 off-peak 塞 2-3 个 5-16 分钟的固定草稿对照（E1.1 的相位级筛选、E3.3 预扫），全流程变体才进夜间；
2. **先筛后跑**：多相位 span 变体先用固定草稿系筛掉明显不可行的相位（输出没降 or 合并失败），只对幸存相位跑全流程——E1.1 的实验成本从 4 个全流程压到 2 个；
3. **分析前置**：L3 在队列跑的同一时刻写"对比表模板+上轮遗留分析"，晨报一出只填数字；
4. **盲评与跑解耦**：E1.2 夜间跑完，盲评材料白天由 L4 去标识后发（评分调用走 off-peak 午间或晚上，flash 评分很便宜）；
5. **失败不回炉**：kill criteria 触发的方向当场归档，禁止"再试一次看看"（v1 的否决记录法）；
6. **窗口溢出处理**：队列超窗时按 gate 优先级截断，余下变体顺延（不压缩单变体预算）。

## 6. 子代理任务包提示词模板

### 6.0 常设守则块（粘贴进**每一个**子代理 prompt 的开头）

```
【常设守则——逐条遵守】
1. 你只改你名下的文件集：<填入>。不碰其他文件；需要交叉改动时在交付物里列"待办"而不是直接改。
2. 交付前自跑相关单测与 lint（python -m pytest tests/ -k <相关> + python scripts/prefix_lint.py），失败不得交付。
3. 禁止删除/清理任何 tests_output/ 下的历史产物；禁止 rmtree 任何 fake home（先留存 usage 与 artifact）。
4. 涉及 prompt 的改动：与基线 byte-identical 只允许目标段不同（变量隔离纪律）。
5. 涉及 API 的配置：价格口径以 docs/成本台账.md 头部为准（flash hit $0.007/miss $0.22/out $0.66，pro ×3，off-peak）；禁止调 peak 时段参数。
6. 台账与文档引用格式与 docs/ 现有文件一致；数字必须给出口径（跑级/相位级）。
7. 单元测试不过 = 交付失败；诚实报告失败原因，不要掩盖。
```

### 6.1 实现类模板（L1/L2）

```

  app/pipelines/ 现有四相位实现（deslop/trim/enrich/review_fix）。
目标：为四相位实现 output_mode=span——模型只返回 [{op:"replace|delete|insert", para_no:N, text:...}]，
  客户端合并成全文。含：span 解析器（容忍 JSON 噪声）、合并器、健全性守卫（合并后 diff 校验：
```
