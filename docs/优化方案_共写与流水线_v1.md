## 二、优化方案设计

### 方案 A：共写对话「讨论 / 撰写」双模式重构 ★本次核心（治 P0-1）

**设计哲学**：共写的本质是"作者与 agent 轮流说话的工作台"，不是"每次输入都收一篇作文"。把**对话**（商量）与**成稿**（产出）拆成两个显式动作，各自的提示词、长度、模型、入口全部分开。

#### A1. 双模式定义（每个共写 Agent 都有这两套配置）

数据结构：`CO_ROLES` 每个 stage 从单一 `role` 扩展为：

```python
CO_ROLES = {
    "cw_core": {
        "agent": "设定 Agent",
        "slot_compose": "writing",      # 撰写用写作槽
        "slot_discuss": "helper",       # 讨论用辅助槽（快、便宜）
        "discuss": "...",               # 讨论模式角色约束（见 A2）
        "compose": "...",               # 撰写模式角色约束（沿用现 role 文本）
    },
    ...  # 六阶段 + supervisor/readback 同构
}
```

#### A2. 讨论模式提示词（核心，逐字设计）

讨论模式的系统约束**硬编码进 prompt 模板**，不依赖模型自觉：

```
【回应模式：讨论】
作者本轮发言：「{user_message}」

你只有三件事可做，按序执行：
① 复述确认：用 ≤3 句话整理你理解的作者意图（「你的意思是——」开头）；
   作者发言与已确定设定冲突时，只指出冲突点与底册依据，不展开。
② 待拍板：列出（如有）≤2 个必须由作者拍板的具体分歧点，每个给一行选项。
③ 等待：明确说一句你在等作者哪方面的输入。

硬性禁令：
- 禁止展开成稿/设定文本/正文段落（那是「撰写模式」的事）；
- 禁止罗列 3 个以上的方案或方向；
- 全文 ≤200 字（作者发言 ≤12 字时 ≤80 字）；
- 作者说「可以 / 好 / 嗯 / 继续 / 就这样」等确认词时，只回「已记录：{一句话概括}」。
```

撰写模式提示词：沿用现 `role` 文本 + `CO_PRODUCT_STRUCTURES` 结构要求 + "直接产出本阶段产物草案"。

#### A3. 模式载体与切换（UI + 状态）

- **载体**：对话输入框旁的分段开关 `【讨论 | 撰写】`（CwDialogueDock，双态按钮，Tab 键切换），当前模式高亮。
- **默认**：每个阶段进入时默认**讨论**模式。
- **状态**：存项目状态 `cw.stage_mode[stage]`（记忆作者偏好，切阶段自动回讨论）。
- **撰写模式的两个入口**：
  ① 开关切到「撰写」后，输入框 placeholder 变为"描述要写什么，直接出草案…"；
  ② 每阶段卡片上常驻一个**「生成草案」**按钮（不发对话，直接按本阶段结构出草案，结果在对话区标「草案」徽标）——想跳过讨论直接要稿的作者一步到位。
- **越权防护**：讨论模式下 agent 输出若 >300 字（模型不守规矩时），bridge 侧截断 + 顶部提示"讨论模式输出过长，已截断——要完整草案请切撰写或点「生成草案」"。

#### A4. 与确定流的衔接（不动既有契约）

SummarizeWorker（确定=总结定稿）**保持不变**——讨论-mode 的转写照样被它总结成产物。这正是共写该有的样子：讨论区聊的是"要不要"，确定时才产出"是什么"。

#### A5. 改动面

| 文件 | 改动 |
|---|---|
| app/prompts/co_writing.py | CO_ROLES 拆 discuss/compose；CO_DIALOGUE_PROMPT 增加 `{mode_block}` 段 |
| app/core/co_dialogue.py | DialogueWorker 接收 mode 参数，选 role 与槽位 |
| app/ui/bridge.py | submitCwMessage 增 mode 参数；新增 generateCwDraft()（生成草案槽） |
| app/core/state.py | cw.stage_mode 状态 |
| app/ui/qml/components/CwDialogueDock.qml | 模式开关 + 「生成草案」按钮 + 截断提示条 |

**验收标准**：① 发「嗯」→ 回复 ≤80 字且不含任何展开；② 发一个想法 → 回复=复述+冲突点+≤2 问，≤200 字；③ 只有切撰写/点「生成草案」才出长文；④ 六阶段全部行为一致。

### 方案 B：全量 DeepSeek 官方模型策略（治 P0-2、P2-10）

**设计**：槽位不再直接绑连接 id，而是引入**角色→档位→连接**的两级解析，配三个出厂预设：

```
模型策略预设（设置页一键切换）：
① 官方全家桶（默认，作者本次指定）：writing = 官方 v4-flash；helper = 官方 v4-flash；review = 官方 v4-flash
② 严格审校：writing/helper = 官方 v4-flash；review/合规对账 = 官方 v4-pro（flash 做严格审校会退化，已实证）
③ 自定义（保留现有手动绑法）
降级链：官方 flash → 官方 pro → 百炼 → 连接表首行
```

- 官方 flash 实测：草稿 79 秒/章、无超时无空流（百炼同任务 5-8 分钟 + 两次 600s 超时）。
- 预设切换 = 改 slots 指向（连接行由应用确保存在，id 固定 `ds-official-flash` / `ds-official-pro`），老配置零迁移。
- 审校票、追踪更新、读改、supervisor 全部跟着槽位走，**一处切换全局生效**。

**验收标准**：审校票 ≤90 秒；追踪更新零 600s 超时；单章循环 ≤12 分钟。

### 方案 C：共写体验修补包（治 P0-3、P0-4）

**C1 落稿提取契约**：prose 阶段 compose 输出强制包裹标记：

```
<<<正文>>>
（正文全文，首行 ## 第N章 标题）
<<<正文完>>>
（之后才允许交接块/给作者的话）
```

bridge 落稿时：有包裹 → 提取包裹内文本；无包裹 → 弹「提取预览」让作者确认首尾（默认按 `## 第N章` 到尾部提取）。评估报告里"开场白混进正文"的问题从契约上消灭。

**C2 锁定链路加固**：supervisor 失败时报告区显示错误 + 两个按钮——「重试比对」「跳过比对并锁定（留痕：supervised=skipped+原因）」。锁定不再被单次 LLM 故障卡死；跳过留下审计痕迹。

**C3 讨论模式红利**：readback（读改 agent）天然符合讨论模式约束，纳入 A1 结构统一管理。

### 方案 D：设定正典治理（治 P1-5、P1-6、P1-8、P1-7）

**D1 设定清算（每章定稿后的自动对账）**——验证①的对账逻辑产品化：

- 触发：每章定稿（G8 后）自动跑一次；
- 动作：抽正文专名+世界观陈述 → 对照世界书三分类（底册有 / 合理补白 / 越界自创）→ 报告区出清单；
- 越界项两个按钮：「收编入册」（写入世界书·追加登记，转正当典）、「待改」（挂到章节备忘，下章细纲前提醒）；
- 模型用 review 档（严格判定不许 flash 单飞，见 F1）。

**D2 拆解工具补专题层**：`decompose_worldbook.py --theme 民生经济` 等专题 passes（平民生计/市政管理/低阶市场/货币/行会规矩），加**覆盖度报告**（哪些层 0 条目，红榜提示）。直接治"铜币/执事堂/验批单"这类洞。

**D3 同人模式**：项目存在 `设定/原作世界书.md` 或创建时导入过世界书 → 自动打 `fanfic` 标记：core/outline 参考块追加注入「世界书摘要 + must 禁则清单（≤800 字）」，细纲 Agent 职责追加"每单元列原作要素出场清单"（同时治 P2-12 标识浓度）。

**D4 must 规则程序化消费**：
- compose 提示词注入「本章相关 must 规则清单（按细纲专名激活，≤15 条）+ 要求逐条写落点」；
- 定稿前核对：有 `pattern` 的规则跑正则（gate 已有能力）；无 pattern 的由审校 agent 填「落点表」（规则 → 本章哪一段落实），填不出的标红进 G8 报告；
- G8 决策门展示对账表，作者一眼看到"哪条规则本章没落实"。

### 方案 E：流水线并行化 + 协作方式（治 P2-9，作者点名的效率问题）

**应用内并行**（改 orchestrator/chapter_microcycle）：
- E1 三张审校票并发（QThread ×3 + 汇总聚合）：审校 17 分钟 → ≤6 分钟；
- E2 四个追踪更新（章节摘要/全局摘要/角色状态/伏笔）并发：取最长一路即完成；
- E3 世界书拆解分块并发（线程池，3-4 路）：拆解 25 分钟 → ~8 分钟。

**助手协作方式**（本次验证执行后的工作约定，作者点名要求）：
- 独立单元（拆解分块、逐章评估、逐章对账、多方案对比）一律后台子代理并行，主线程只做统合与裁决；
- 子代理任务书必须自带全部上下文（文件路径+口径+输出格式），不依赖会话记忆；
- 长任务（>5 分钟）一律后台化 + 轮询心跳，不阻塞主对话。

### 方案 F：评估与合规判定升级（治 P2-10、P2-11、P2-13）

- F1 **审校分层**：日常 3 票 = flash；6 维终审与设定清算 = pro（已实证 flash 严格判定会字段级退化）；退化检测器——JSON 输出的 `why` 字段去重率 >30% 即判退化，自动换 pro 重试。

## 三、实施顺序（建议）

| 阶段 | 内容 | 理由 |
|---|---|---|
| Phase 1 | 方案 A + B + C1/C2 | 作者最痛的共写体验 + 模型提速，改动集中在共写链路，可一起验收 |
| Phase 2 | D1/D2/D4 | 世界观纪律（验证①的核心教训），依赖 Phase 1 的模型策略 |
| Phase 3 | E + F + D3 + G | 效率与产品化 |

## 四、明确不做的（防方案膨胀）

- 不改自动档六阶段产物结构（`CO_PRODUCT_STRUCTURES` 是跨档契约，TUI 读取器硬依赖）；
- 不做世界书全量注入 prompt（预算爆炸），只做"摘要+禁则清单"（≤800 字）；
- 不推翻槽位路由架构，只加"角色→档位→连接"解析层；
- 讨论模式不做多轮自动追问（agent 只等作者，不抢话）。

## 五、验收口径（作者评审用）

每条方案都给了可测验收标准。整体验收 = 用同一份斗破底册重跑双档位第 1 章：
1. 共写档：发 10 条短消息，平均回复 ≤200 字、零发散；点「生成草案」才出稿；
2. 单章耗时 ≤12 分钟（自动档全循环）；
3. 世界观对账报告：越界项在定稿当时被点名并给出收编/待改选择，第 2 章不再出现未清算的自创；
4. 评估子代理复评 ≥ 上轮分数（自动档 ≥81），人话度 ≥8。

# v1.1 增补（作者反馈：断点续跑 + 协同效率）

## 六、新增问题 P0-14：章内任何位置停止 = 前面全部白做 ★★★

**作者原话**：无论在流水线哪个地方停止，前面所有的内容都会消失。理论上停在审核，继续时应该紧接着重新审核（保住草稿与已投票数），而不是全部丢失。

**代码级根因（已核实）**：

1. 章内微循环（`stages.chapter_microcycle`）有 7 个步骤：组装 → 草稿 → 扩写 → 扫描(G6) → 去味(G7) → 审校 → 定稿落库(G8/G9)。每步都有 `ctx.step()` 标记——**但这些标记只发 UI 信号，不落盘**（pipeline_state.json 里 `current_step: null`）。
2. 草稿、扩写结果、去味后文本、已投的审校票（1/3、2/3）**全部活在内存里**；正文文件要到最后"定稿落库"才**首次**写盘。
3. 恢复逻辑按文件判定：`first_missing_chapter()` ——正文文件不存在 = 整章缺失 = 从 G5L 起全量重跑。
4. 结论：停在审校 → 草稿蒸发 → 整章重写。停在 G8 门 → 同样。**用户停得越晚，损失越大**——与断点续跑的直觉完全相反。

## 方案 H：章内步骤级断点续跑（治 P0-14）★与方案 A 同级优先

### H1 核心原则：**草稿即文件，定稿只是状态迁移**

草稿完成后**立即写盘**到正文文件（`正文/第N章_*.md`），状态标 `draft`；后续去味/审校/定稿都是对这份文件的**原地修订 + 状态推进**。由此"停在哪"天然有据可查——文件系统就是 checkpoint。

### H2 步骤级 checkpoint 状态

`pipeline_state.json` 新增章内状态（每步开始/完成时原子写入）：

```json
{
  "chapter_step": {
    "num": 3,
    "step": "review",              // assemble|draft|enrich|scan|deslop|review|finalize|tracking
    "draft_path": "正文/第003章_xxx.md",
```

### H3 恢复语义表（回答"停在审核，继续时发生什么"）

| 停止位置 | 重启后的行为 | 保留的 |
|---|---|---|
| 细纲生成中 | 重跑细纲（幂等） | 已有前两章细纲 |
| 草稿流式中 | 重写草稿（半篇无法续写，成本可接受） | 上下文组装结果（秒级） |
| 字数扩写中 | 基于盘上草稿重跑扩写 | 草稿 |
| AI 味扫描/去味中 | 重跑扫描+去味（秒到分钟级） | 草稿 |
| **审校中** | **草稿原样保留；已完成的票保留；只补投剩余的票**（如 1/3 → 只投 2 张） | **草稿 + 已投票数** |
| G8 门等人 | 重启后重新触发 G8 决策门（gate_status 已持久化，恢复时重新 emit），审校结论在盘 | 全部 |
| 定稿落库中 | 幂等重做（写文件+版本归档本就幂等） | 草稿 |
| 追踪更新中 | 幂等重跑（本来就是"失败不阻断"） | 已定稿正文 |

## 七、协同工作模式（作者点名要求，正式立项为工作约定）

作者明确：**不怕时间长，怕效率慢；要用多个子代理协同工作。**此约定同时适用于（a）本助手的工作方式、（b）应用内流水线（方案 E 已含）。

### 7.1 本助手的协同规则（从下一轮任务起生效）

1. **任务分解先行**：动手前先把任务切成互相独立的单元（拆解分块、逐章评估、逐章对账、多方案对比、多文件互不相干的修改），列出并行计划再动手。
2. **后台子代理并行**：每个独立单元派一个后台子代理（run_in_background），任务书自带全部上下文（文件路径、口径、输出格式、JSON 摘要行），不依赖会话记忆。
3. **主线程只做统合**：收集子代理产出 → 冲突裁决 → 汇总报告；主线程不串行等待任何可并行的单元。
4. **长任务一律后台化 + 轮询**：>5 分钟的任务不阻塞主对话，定期心跳汇报。
5. **本次验证的反例**（引以为戒）：拆解 7 块串行跑了 25 分钟（本可 3 路并行 8 分钟）；两次章节评估串行（本可并行）。同类场景不再发生。
