## 1. 目的与设计原则

### 1.1 四个目的（不服务于这四件事的测试不进本计划）

| # | 目的 | 产出物 | 消费者 |
|---|---|---|---|
| P-1 | **量化能力与水平** | 能力评分卡（§4）+ 判据表（§6） | 用户（决定能不能给别人用/发版） |
| P-2 | **发现并定性缺陷** | 缺陷台账（另文件），每条带复现命令与验收判据 | 主代理（排期） |
| P-3 | **定义下一次迭代内容** | 迭代卡清单 + Exit criteria | 主代理/用户 |
| P-4 | **防回归** | 全层门禁（L0-L9）+ 反作弊条款（§9） | 后续所有迭代 |

### 1.2 六条原则

1. **判据预注册**：阈值先写死在 §6，测后不改；不达标就是发现，不许临场放宽（V9 的教训：口径一松，结论就假）。
2. **E1/E2/E3 分级**：只有 E1（有 usage/产物/日志证据）能进评分卡分子；E2 打折 0.7；E3 计 0 分且不许驱动决策。
3. **红门封顶**：提交态上存在的红门（不是「未测」）把所在域压到 60% 上限——门红着，能力就不许评为「合格」。
4. **可复算**：评分卡由 `scripts/capability_score.py` 读 [`0.20.4_判据表.json`](0.20.4_判据表.json) 复算，任何人可重跑得同分；不靠文档里手写的数字。
5. **反作弊**（§9）：时序断言不算行为断言、驱动文本不算产品产出、同源评委不算独立证据、冻结基线不许随实现悄悄改。
6. **成本可控**：离线层 0 元、可全自动；实弹层按批预算上限执行，超 1.5× 预算全停（沿用 [测试接手指南_v1](测试接手指南_v1.md) §7）。

## 3. 能力模型与评分规则

### 3.1 五级能力刻度（每域独立判定，再汇总）

| 级 | 名称 | 判定条件（全部可机器判） |
|---|---|---|
| **L0** | 未建 | 无实现，或只有文档承诺 |
| **L1** | 建了未接线 | 实现存在但生产路径不经过（`app/` 内零消费），或默认关闭且无验收 |
| **L2** | 接线未验证 | 生产路径经过，但无自动化验证（只能人工跑一次看看） |
| **L3** | 离线验证 | 单测/根测试/探针覆盖并通过，且**无提交态红门** |
| **L4** | 实弹验证且达标 | 真机实跑 + 预注册判据达标 + 留证可复查（E1） |

### 3.2 计分公式（可复算）

```
子项得分 = 权重 × f(实测/目标) × 证据折减
f(x) = min(1, x)                    （越高越好：绿率/覆盖率/达标率）
f(x) = min(1, 目标/实测)             （越低越好：成本/token/flaky 率）
证据折减 = 1.0（E1） / 0.7（E2） / 0（E3）
域得分 = Σ子项得分；若该域存在「提交态红门」，域得分 = min(域得分, 0.6 × 域权重)
能力总分 = Σ域得分（满分 100）
等级 = <40 L1 / 40-59 L2 / 60-79 L3 / 80-89 L4 / ≥90 L5
```

封顶条款只对**红门**生效，不对「未测」生效（未测按子项 0 分计入，不封顶）——否则「不测就不会被罚」，与目的相反。

## 9. 反作弊与口径纪律（十条）

1. **时序仪器不算断言**：任何依赖墙钟/并发的断言必须改为注入接缝（V5 的 429 用例是反面教材）。
2. **驱动文本不算产品产出**：离线脚本补写的字数、离线改写的稿子必须与产品路径分账（V9）。
3. **同源评委不算独立证据**：评委与写手同模型时，只许作臂间相对比较，不许报绝对分（J-15）。
4. **冻结基线更新须留证**：`--update-baseline` / 快照重新 bless 必须在提交说明里逐条写明理由，并与设计变更同一提交（否则哨兵形同废除）。
5. **探针不许比被测代码年轻**：改产品接口必须同批改探针（本轮 `probe_wb_import` 因 `project.wb` 壳拆除而崩，是典型）。
6. **红门不许绕过**：不许改产品代码绕过失败测试（[测试接手指南_v1](测试接手指南_v1.md) §9 红线 6）；失败是数据。
7. **运行态不入库**：测试/探针跑完 `git status --porcelain` 必须只含预期改动（J-38）。
8. **判据预注册**：阈值写在 §6，测后不改；要改就另开裁决。
9. **E3 不许驱动决策**：没有证据的结论不许进报告、不许立项。
10. **成本与隐私红线**：长测/盲评不许污染用户官方控制台数据；失败现场必须过 `redact_text`。

## 10. 风险、回滚与红线

| 风险 | 触发条件 | 处置 |
|---|---|---|
| 实弹批超预算 | 单批 >1.5× 预算或单章 >¥0.8 | 全停，写晨报，等用户裁决（`offpeak` 门 + `bench_queue` 3 连败熔断） |
| 上游不可用（429/下线） | 连续 3 章失败 | 换渠道须留痕；不许静默换（红线 5） |
| 修复引入回归 | B1-B5 后单测出现新红 | 立即回滚该文件（`git checkout -- <file>`），红转绿再继续 |
| 冻结基线误更新 | 有人用 `--update-baseline` 抹平漂移 | 反作弊 §9.4：提交说明缺理由即拒绝合并 |
| 探针腐化扩散 | 产品接口变更未同步探针 | 每批 B2 前先跑一遍舰队，红支先修再继续 |
| 备份单点 | 磁盘故障 | B8 内补 bundle + 异地副本；无 remote 期间每次验收后打 bundle |

**红线**（继承并强化）：不许用驱动脚本冒充产品路径；不许把测试改绿代替修缺陷；不许在 CI 之外宣称「全绿」。
