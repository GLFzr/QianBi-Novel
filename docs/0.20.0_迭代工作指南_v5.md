## W-01 · 思考型模型的预算与"空内容重发"（P0，最高优先）

**实测（真端点）**：一次共写讨论 `completion=2434` 中 `reasoning=2297`（**94%**），可见回复 184 字；
`max_tokens=2048` 的正经写作请求 ⇒ `finish_reason=length` + **可见内容为空**，应用判"模型返回空内容"
后**用同一个 payload 原样重发**（本机＝白等两遍，云端＝白付两遍）。

**根因（三层，逐条要修）**：

1. **自救分支的守卫写错了对象**：`client.py:418` 是 `if payload.get("thinking") and not last_degraded`
   ——判的是"**我们有没有下发 thinking 参数**"，不是"**模型有没有在思考**"。出厂连接**不带 `thinking` 键**
   （实测 `ds-official-flash` 等四条均 `<无此键>`），且 `BUILTIN_PHASE_PARAMS` 只覆盖 6 个机械相位
   （`tracking/chapter_summary/global_summary/deslop/enrich/review`）⇒ **`prose`、`core`、`volume`、
   `worldbook_*`、`blurb`、`dialogue`、`backflow`、`review_fix`、`trim` 这些相位：模型默认思考开、
   自救不触发**。注释里那句"v15 每章 6 笔空流×3 的真凶"就是同一故障的历史现场。
2. **缺 provider 能力表**：怎么关思考各家不同 —— DeepSeek 系 `thinking:{type:"disabled"}`；
   vLLM / llama.cpp / LM Studio 走 `chat_template_kwargs:{thinking:false}`；OpenAI o 系只有
   `reasoning_effort` 降档；**什么都不支持的端点，唯一有效手段是抬高该次预算重发**。
3. **重试语义**：对"`length` 截断导致的空内容"，同 payload 重发必然同样失败 ⇒ 必须与首发不同，
   否则直接判失败并把原因说清（不许伪装成"网络抖动"再烧一次预算）。

**做法**：新增 `_thinking_off_variants(conn)` 能力判定 → 空内容且 `finish_reason in (length,)` 时按
能力顺序选一种降档（关思考 → 降 effort → 抬预算），**每次重发 payload 必须与上一发不同**（可断言）；
不支持任何开关时抬预算一次，仍空则失败并给可读原因（含"该端点思考与正文共用 max_tokens 预算"提示）。

**验收（全部主代理亲手）**：
- 离线假端点（不发网络）：`thinking` 不下发时只回 reasoning ⇒ 断言"第二次 payload ≠ 第一次"且"最终成功或明确失败"，
  撤掉修复必须红；
- 三类端点各一条能力表用例（DeepSeek / chat_template_kwargs / 无开关）；
- **真端点复测**：同一句写作请求 `max_tokens=2048` 打本机 bonsai，修前"两笔相同请求"、修后"第二笔必须不同"，
  用 `.dialogue` 账本两行的 `note`/payload 指纹作证据；
- 流式路径（`_stream_messages`）同规则不得漏。

## W-02 · `outline` 的 `reasoning_effort:"low"` 从未随请求下发（P1）

`client.py:329` 规定 `effort` 仅在 `thinking=="enabled"` 时下发；出厂连接无 `thinking` ⇒ 细纲降档**是空操作**
（代码里那句一次性警告"该参数不会随请求下发"正是此事），而注释仍写着它是"outline 38k 输出/笔的主因"的对策。
**做法**：把 outline 档改成能真正生效的形态（`thinking:"disabled"` 或显式 `enabled`+`low`），
并用 payload 断言钉住"该参数确实进了发出去的那份 payload"。**验收**：删掉修复 ⇒ 断言红。

## W-04 · 探针隔离从"快照还原"升级为"进程隔离"（P1）

现状：探针靠 `probe_guard.arm_config_guard()` 快照 + **atexit 还原**。实测它被污染过两次：
探针被超时杀掉时不还原；而 `QIANBI_CONFIG_DIR` 挡不住 **Windows 凭据管理器**（我的种子 token 被
`save_config` 脱水写进了真 keyring，事后已删）。
**做法**：`arm_config_guard()` 改为①设 `QIANBI_CONFIG_DIR` 到临时目录（若 `app.config` 已导入则同时改
`CONFIG_DIR/CONFIG_FILE/_LEGACY_DIR`）；②把 `secrets.SERVICE` 指到测试专用服务名，凭据写进可丢弃命名空间；
③保留快照还原作第二道。**验收**：一支探针跑到一半被 `kill` ⇒ 线上 `config.json` md5 不变（现在会脏）。

## W-05 · 立项阶段拒绝对话时，用户那句话被丢弃（P1，尺 5）

`bridge.py:4025-4027`：`stage == cw_project` 时先 `toast(warn)` 再 `return`，而 `transcript_append(user)`
在其后 ⇒ 用户输入**不留任何痕迹**，"我说了话，它没反应"。`generateCwDraft` 同型（:4039）。
**做法**：先留痕再拒绝（用户条 + 一条系统拒因），并保证拒因可回看；提示语从"请填写左侧表单"升级成
"这一步我能替你做什么"（指路）。**验收**：新探针断言"被拒的发言进转写、拒因进转写"。

## W-06 · 走查驱动器的终态判据太窄（P2）

`pump_until(..., 420)` 只认"转写新增 assistant 行 / 阶段变了"，**不把"被拒"和"失败回执"当终态**
⇒ 一次正常拒绝白等 7 分钟（本机走查实测）。**做法**：终态加"出现 warn/error 回执"，并把超时降为可配、
失败时打印最后一屏 toast 与 `.dialogue` 尾行。**验收**：对着未填表单的项目跑 `discuss`，应在秒级返回 FAIL 并带原因。
