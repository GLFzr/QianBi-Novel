## 一、现状诊断（数据与代码双重实锤）

### 1.1 账单实测（2026-09-05，规模验证连跑 10 章）

| 项 | tokens | 占比 |
|---|---|---|
| 输入（命中缓存） | 212,480 | **16.1%**（212,480 / 1,317,716 输入合计） |
| 输入（未命中缓存） | 1,105,236 | 83.9% |
| **输出** | **2,837,374** | 全部 token 的 **68%** |

两个结论：
1. **输入命中率仅 16.1%**——目标 ≥90%，相差 5.6 倍。
2. **成本大头不是输入，是输出**：输出是输入总量的 2.15 倍。原因：`thinking=max`
   连接级全局生效，DeepSeek 把推理 token 计入 output 计费——**每次调用都付最高档
   推理税**，包括根本不需要深想的机械调用（追踪更新/章节摘要/去味改写）。

### 1.2 代码级诊断（本仓实测，非猜测）

| # | 缓存杀手 | 实测证据 |
|---|---|---|
| K1 | **共享前缀过短**：两章草稿 prompt 公共前缀仅 ~3,330 字符（core_setting 1500 + genre 5 + worldbook 1825），prompt 全长 9-10k | 实测两章 draft 前缀对比：worldbook 按章激活（num 参数）位于中段，两章即断 |
| K2 | **命中率不可观测**：`_record_usage` 只读 `prompt_tokens/completion_tokens`，丢弃 DeepSeek 返回的 `prompt_cache_hit_tokens / prompt_cache_miss_tokens` | client.py:117-118 |
| K3 | **思考预算无相位分层**：`thinking/reasoning_effort` 挂在连接上全局一个值；`_overrides(phase)` 相位机制存在但未覆盖 thinking | client.py:207-228 |
| K4 | **共写对话 append-only 红利浪费**：`{transcript}` 之前有 4 个动态段（mode_block/handoff/reference_block 等），模式切换或 handoff 更新即全前缀作废 | CO_DIALOGUE_PROMPT 结构实测 |
| K5 | **世界书两段未拆**：常驻条目（章章相同）与激活条目（章章不同）混在一个 `worldbook_text()` 里，位置在中段 | K1 实测的断裂点 |
| K6 | **正面项**：审校 3 票 prompt 实测逐字一致（3 票中 2 票应高命中）——但无观测数据确认 | build_final_review_prompt ×2 对比 |

### 1.3 DeepSeek 官方与 harness 研究结论

来源：[DeepSeek 官方 Context Caching 文档](https://api-docs.deepseek.com/guides/kv_cache/)、
[deepseek-harness 99.93% 命中率报道](https://www.htx.com/news/cache-hit-rate-reaches-9993-the-best-harness-for-deepseek-is-7o7Tuu5n/)、
[HN 讨论（agent 循环重排上下文 → 命中率 <20%）](https://news.ycombinator.com/item?id=48257509)、
[Digital Applied：动态内容移出前缀使命中率 7%→84%](https://www.digitalapplied.com/blog/prompt-caching-2026-cut-llm-costs-engineering-guide)。

**缓存三定律**（全部研究的交集）：
1. **逐字节位置性**：前缀按位置精确匹配，一个字节不同，从该字节起全部作废——
   缓存以"完整前缀单元"存取，改中间等于后面全 miss；
2. **静态前置、动态殿后**：system/工具/长文档/规范放最前，用户唯一内容放最后；
   时间戳、随机数、日期进前缀 = 缓存杀手；
3. **append-only**：多轮上下文只增不改（A+B → A+B+C 命中；A+B → A+C 全废）。

harness 达到 99.93% 的做法没有魔法：**把"会变的"全部挪出前缀**，system+工具 schema
逐字节钉死，`--nano` 模式甚至把固定载荷压到 ~2K token。他们报告的基线 agent 只有
62%——我们 16% 的问题不是 DeepSeek，是 prompt 结构。

## 二、总体优化目标（能力轮规模验证 + 体验轮合并）

### 成本/体验（本轮主目标）
- **G1 输入缓存命中率 ≥90%**（口径：`prompt_cache_hit_tokens / (hit+miss)`，连跑 3+2 章实测）
- **G2 单章输出 token ≤ 现状 50%**（相位化思考预算 + max_tokens 收紧）
- **G3 单章综合成本 ≤ 现状 1/3**；单章墙钟 ≤ 现状 2/3
- **G4 成本可观测**：hit/miss/费用按 phase 落盘聚合，命中率 <80% 自动告警

### 写作能力（上轮遗留收尾）
- **G5 正文→日历/台账自动回写**（去掉人工卫生轮，R9 已人工示范完整流程）
- **G6 清算器误报率 <10%**（定级纪律 R8 已升级，需实测验证）
- **G7 场景切换硬指标**（根除 ch5-6 型连续静态双章：番茄竞争力 6.5 的教训）
- **G8 连写第 11-20 章**（黑岩城线）——同时作为 G1/G2 的实测场

## 三、方案 A：稳定前缀架构（治 G1，主工程）

### A1 共享前缀构建器 `shared_prefix_builder(proj)`（核心）
一个函数产出**逐字节稳定**的项目级头部，全部调用族（草稿/扩写/去味/审校/追踪/清算/
细纲/摘要）统一接在头部之后：
```
[项目头 = 全调用族逐字节一致]
  01 写作纪律全文（writing.py 的 14+2 条硬约束）
  02 题材预设块（genre_block）
  03 核心设定节选（金手指约束条款/授权自创清单/读者契约——截断口径固定）
  04 must 规则全文（正则.md 全量，不再按章裁剪）
  05 世界书·常驻条目（[常驻] 标记的全部条目，按名称排序固定输出）
[阶段段 = 每种调用族内部一致]
  该阶段的模板规则与产物结构要求
[动态尾段 = 每次调用自然不同]
  本章细纲 / 上一章结尾 / 近章摘要 / 角色状态 / 激活条目 / 用户指导
```
规则：**项目头内禁止出现**章号、日期、`num` 参数、任何随章变化的内容。
各模板现有字段重排进三层，语义不删只挪。

### A2 世界书两段式 API
`wb.assemble` 拆为 `assemble_constant(proj)`（常驻条目，进项目头，全章全调用一致）
与 `assemble_activated(proj, num, anchors)`（关键词/章节激活条目，进动态尾段）。
`worldbook_text` 保留为两者拼接的兼容出口（自动档旧路径零回归）。

### A3 确定性序列化
- 全仓扫描 prompt 链路上的 `datetime/strftime/random/uuid`（初扫 writing/planning 无命中，
  需扩展到 scene_cards/presets/genre_block）
- 台账/清算/世界书排序全部固定（`sort_keys=True`、按 name/last_ch 排序输出）
- `worldbook_text` 激活条目输出顺序按 (触发优先级, 名称) 双键排序，杜绝并列抖动

### A4 复用族治理
- 审校 3 票已逐字一致（K6）——保持；**并给 votes 3→2 的降档开关**（命中率上去后
  前 2 票的边际价值下降，可配 `review_votes: 2`）
- 扩写/去味第 2 轮天然断前缀（prose 变了）——接受；项目头仍共享
- 重试（空流/超时重发）天然全命中——零成本收益

### A5 共写对话 append-only 修复
`{transcript}` 之前的 4 个动态段（K4）重排：项目头 + 阶段规则置顶，
`mode_block/handoff` 移到 transcript 与 user_message 之间——同模式连续对话即命中。
模式切换（讨论↔撰写）本来就意味着话题切换，断前缀可接受。

### 预期测算
项目头约 4-6k tokens；单章 15-20 次调用共享（章内命中）+ 跨章命中（数小时内缓存
未清理时连跑天然命中）。对照 harness 99.93% 与基线 agent 62% 的差距全在结构——
**90% 目标可达，且主要收益在连跑场景**（正是花钱最多的场景）。

## 四、方案 B：输出 token 治理（治 G2，最大的省钱项）

账单里输出 2.837M 是输入的 2.15 倍——**只优化缓存，最多省输入的 85%；优化思考预算，
直接砍最大头**。

### B1 相位思考预算表（挂 `_overrides(phase)` 现成机制）
| phase | thinking | effort | 理由 |
|---|---|---|---|
| outline / core_setting / worldbook_gen | enabled | max | 结构创新需要深想 |
| prose（草稿） | enabled | high | 质量敏感，但 max 边际收益低 |
| enrich / deslop | **disabled** | — | 定向改写，不需要发散思考 |
| review（终审票） | enabled | max | 严格判定（R7 实证 flash 低档会退化，思考保留） |
| review_fix | enabled | low | 修复有明确靶子 |
| tracking / chapter_summary / global_summary | **disabled** | — | 机械抽取/一句话摘要 |
| canon_audit | enabled | high | 合规判定需要，但 prompt 已收紧 |
| co_dialogue（讨论模式） | enabled | low | 短回复不需要深想 |
| co_dialogue（撰写模式）/ co_summarize | enabled | high / max | 同写作档 |

实现：`OPTIONAL_PARAM_KEYS` / `_overrides` 相位表增加 `thinking`/`reasoning_effort`
两个键（连接值作默认、相位覆盖、`stage_params` 可再覆盖——三层现有解析不动）。

### B2 max_tokens 收紧
全局 65536 → 按任务给：草稿 16k、审校 12k、摘要 2k、追踪 8k（防失控长尾）。

### B3 输出超长熔断
单调用 completion > 20k 记 warning 并入报表（发现病态循环调用）。

预期：输出 2.837M → 约 1.2-1.5M（**-50%±**），且机械相位关思考同时降低墙钟
（追踪更新从 200-600s 降到 <30s，直接治"卡很久"的体感）。

| 阶段 | 内容 | 验收 |

## 八、风险与对策

- **重排伤质量**：提示词重排只挪位置不改语义；用 R7 已验收的第 3 章做重排前后 A/B
  （同章重写，8 维评分对比不回退才合并）
- **thinking 降档伤审校**：review 保留 max（R7 实证低档退化）；降档先从机械相位开始，
  逐相位 A/B
- **缓存几小时清理**：跨天调用不指望命中；连跑（花钱最多的场景）天然在窗口内
- **共写模式切换断前缀**：语义上必要（话题切换），接受

## 九、明确不做

- 不引入 `prompt_cache_key` 类非标参数（DeepSeek 无此参数，靠前缀即可）
- 不做"牺牲质量的极致压缩"（如砍审校票到 1 票——质量回退的代价远超省的 token；
  命中率上去后 3 票成本已大幅下降）
- 不在 P2 前动世界书装配语义（两段式只是拆分出口，激活逻辑不动）
